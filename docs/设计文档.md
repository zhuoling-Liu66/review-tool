## 1. 背景与目标

把企业级代码审查机制（变更塑形 → 预提交验证 → 必过 CI → AI Review → 安全审查 → 人工审批 → 合并发布 → 学习闭环）降维为单人或小团队可运行的流水线。核心不是"上多 Agent"，而是用确定性工具兜住下限、按风险分配 AI 成本、用证据和账本满足审计要求。

### 1.1 目标

1. 同一条流水线同时服务本地 CLI、git hook、CI 三种入口，本地能过、线上也能过。
2. 每次变更留下可复核的证据：检查输出、上下文摘要、AI 结论、投票记录、审批记录。
3. AI 审查按风险分档（Quick / Standard / Deep），低风险轻审、高风险深审，预算硬上限。
4. 全链路可审计：模型与提示词版本、diff hash、finding 生命周期、审批人和时间，账本只追加。
5. 合并质量有护栏：以回滚率、事故率不上升为前提优化成本。
6. 多 Agent 的规模与 Deep 比例由评测数据决定，开关始终可退回单 Agent；不默认全量深审。

### 1.2 非目标

- 本工具不自动修改代码、不自动合并、不自动部署；外部编码 Agent 消费 fix-request 的外层环见 [ADR-0002](./ADR-0002-开发Agent外层闭环.md)，其修复仍需审批与 CI。
- 不替代高风险人工审批；工具只能记录审批，不能真正"制造第二个人"。
- 不做多租户 SaaS、组织级 BI 面板、IDE 插件（M4 前）。
- 不执行模型生成的任意命令或测试代码。
- 不做线上 APM / 事故管理，只对接其结果。

### 1.3 成功标准（初始目标，需用自有数据校准）

| 类别 | 指标 | 目标 |
|---|---|---|
| 覆盖 | 有 AI review 的 PR 占比 | ~100% |
| 覆盖 | finding 有明确处理结果的比例 | >95% |
| 噪音 | 驳回率（按错误/有意/无所谓分类） | 逐月下降 |
| 噪音 | 干净集误报数 | 逐月下降 |
| 收敛 | 一轮通过率 / 平均轮次 | 参考 78% / 1.32（原文口径） |
| 收敛 | ≥3 轮占比 / 人工 reset 次数 | 观察，初始 ≤5% / 尽量为 0 |
| 成本 | 每 PR token 与金额 | 不超预算 |
| 护栏 | 回滚率、事故率 | 不上升 |
| 护栏 | 合并时长 | 不显著变慢 |

参考值来自原始方案（企业实践口径），不构成对本仓库的承诺；M4 起以 golden set 实测值为准。

原文的"≥5 轮占比 1.5%"产生于未设置自动轮次上限的流程。本方案自动 AI 审查硬上限为 3 轮，因此不把 ≥5 轮作为目标，改为观测 ≥3 轮占比与人工 reset 次数；若将来放宽上限，再恢复原口径。

### 1.4 硬约束

- 单人维护，工具需跨 Windows / macOS / Linux；避免 bash-only 脚本。
- 无长期服务端：状态存放在仓库 `.review/`、CI artifact 或可选的专用账本分支；不做常驻数据库服务。
- 免费 CI 额度内可运行；AI 不可用时必须能降级而不是卡死。
- 敏感仓库必须支持"仅本地模型"或"脱敏后再送云端"。

## 2. 设计原则

1. **确定性检查优先。** format / lint / type / test / secrets / deps 先跑；确定性检查失败直接阻断，不花 AI 预算。
2. **按风险分配成本。** 小改动与文档走轻量路径；敏感路径才用多视角 Finder + 多 Verifier + 强模型。
3. **AI 不替代"人"的名额。** 低风险可自审放行（带证据与冷静期），高风险必须外部 reviewer；工具不伪造职责分离。
4. **先严后松。** 默认 medium 档；低风险路径需显式匹配；敏感路径是硬地板，不能通过参数静默降级。
5. **审计默认开启。** 每个决策有原因（policy reasons）、每个 finding 有生命周期、每次调用有模型与提示词版本。
6. **有界协作。** 审查内部 Agent 之间不自由对话，只经编排器做结构化 fan-out / fan-in；外层编码 Agent 的修复环只通过工件通信（[ADR-0002](./ADR-0002-开发Agent外层闭环.md)）。不执行模型命令；上下文由编排器确定性地提供。

## 3. 总体架构

### 3.1 组件图

```
         本地 CLI               git hooks               GitHub Actions
             │                      │                        │
             └──────────────────────┴────────────────────────┘
                                    │
                         ┌──────────▼──────────┐
                         │   Pipeline Engine    │  唯一实现，三种入口共用
                         └──────────┬──────────┘
                                    │
   ┌──────────────┬─────────────────┼──────────────────┬───────────────┐
   │              │                 │                  │               │
┌──▼──────┐  ┌────▼─────┐  ┌────────▼────────┐  ┌──────▼──────┐  ┌─────▼──────┐
│ Checks  │  │ Policy   │  │ Context Builder │  │ AI Layer    │  │ Store      │
│ 插件     │  │ Engine   │  │ diff/调用方/测试 │  │ Router →    │  │ findings   │
│ format  │  │ 风险分级  │  │ 裁剪/脱敏/哈希   │  │ Finders →   │  │ ledger     │
│ lint    │  │ 预算     │  └─────────────────┘  │ Ground →    │  │ evals      │
│ test    │  │ 信任     │                       │ Verifiers → │  └─────┬──────┘
│ secrets │  │ 审批档   │                       │ Aggregate   │        │
│ deps    │  └──────────┘                       └─────────────┘        │
└─────────┘                                                            │
                                    ┌──────────────────────────────────┘
                                    ▼
                         Reporters: 终端 / Markdown / GitHub / SARIF
                                    │
                         Approval & Gate（阻断/冷静期/人工）
```

### 3.2 组件职责

| 组件 | 职责 | 不负责 |
|---|---|---|
| Entrypoints | CLI、git hook、CI 统一调用；参数归一化 | 不实现审查逻辑 |
| Pipeline Engine | 编排阶段、取消/重试/幂等、预算扣减、状态持久化 | 不判断代码质量 |
| Policy Engine | 风险定档、模式路由、预算上限、审批方式、敏感路径地板 | 不调用模型 |
| Checks | 确定性工具执行、证据归档、阻断判定 | 不调用模型 |
| Context Builder | 构造每个 Agent 的上下文、裁剪、脱敏、哈希、缓存键 | 不做语义判断 |
| AI Layer | Finder / Grounding / Dedupe / Verifier / Aggregate | 不执行命令、不做审批 |
| Store | findings、run manifest、审批、账本、评测结果 | 不生成报告文案 |
| Reporters | 终端、Markdown、GitHub Review、SARIF | 不改 findings |
| Approval & Gate | 评估阻断条件、冷静期、审批有效性 | 不代替人做高风险判断 |
| Eval Runner | golden set 回放、指标对比、回归告警 | 不参与 PR 阻断 |

### 3.3 一个引擎、三种入口

| 入口 | 运行内容 | 阻断方式 | 典型耗时 |
|---|---|---|---|
| git hook | 快速子集：format/lint（项目命令）、pre-push 全部 blocking 检查 | 本地退出码 | 10–60s |
| CLI | 完整流水线，可 `--no-post` 只看报告 | 退出码 | 1–10 min |
| CI | 完整流水线 + 发评论 + 审批门禁 + 账本 | required check | 2–12 min |

三种入口必须调用同一个 Pipeline Engine 和同一套配置；hook 只允许通过 `phases` 参数跳过某些阶段，不允许另写一套规则。CI 状态检查是最终权威，本地结果为预演。

### 3.4 关键设计决策

| 决策 | 理由 | 代价 / 备注 |
|---|---|---|
| 固定 DAG 编排，自写执行层，不引入 Agent 框架（[ADR-0001](./ADR-0001-编排框架选型.md)） | 成本、延迟、可审计、可复现；角色拓扑是确定的；账本/预算/审批必须自管 | 不支持开放式自主规划；LangGraph.js/Mastra 仅在切换条件满足时评估 |
| Agent 星型通信，只经编排器 | 无死循环、无上下文串味、易审计 | 需要更多编排代码与 schema |
| 审查 Agent 不持有文件系统/网络工具 | 上下文由 Context Builder 确定性提供，防越权与失控 | 跨文件检索能力受限，M4 可加只读检索 |
| 确定性 grounding 先于投票 | 先消掉"文件/行号不存在"的幻觉，省验证成本 | 语义误报仍需 Verifier |
| 账本 JSONL 为事实源，SQLite 为读模型 | 追加不可变、可重建、易导出；审计友好 | 写入需顺序化，崩溃后需重建索引 |
| 审批绑定 diff hash + head SHA | 新提交自动使旧审批失效 | rebase 同 patch 时需明确复用策略 |
| 敏感路径为硬地板 | 防止"文档小改动"夹带 CI/auth 修改被轻审 | 可能增加少量高成本审查 |
| 多 Agent 按档启用 | 低成本路径不背多 Agent 成本 | 需要 eval 决定何时升级 |
| 默认全量记录，默认少发通知 | 审计完整，PR 噪音低 | 报告折叠、避免重复评论 |

## 4. 分层流程映射

| 层 | 企业做法 | 本方案实现 | 阻断点 | 成本 |
|---|---|---|---|---|
| 0 变更塑形 | 小 PR、可回滚 | diff 规模告警（>400 行建议拆分）；PR 模板强制 What/Why/Testing/Risk/How to revert | 告警，不默认阻断 | 无 |
| 1 预 PR 验证 | Agent 跑测试并展示证据；新上下文子 Agent 复审 | pre-commit / pre-push hook；CLI 产出证据；AI 审查使用全新上下文 | 本地失败阻止 push | 低 |
| 2 必过 CI | lint/type/多平台测试/构建 | GitHub Actions 调同一引擎；required check | 红灯阻断 | 免费额度 |
| 3 AI Review | 多 Agent 并行 + 验证投票 + 严重度 | Quick / Standard / Deep 三档；Finders → Grounding → Dedupe → Verifiers → Aggregate | blocker finding 阻断 | 中 |
| 4 安全审查 | 独立 pass，发现即阻断 | gitleaks + Semgrep + osv-scanner 确定性阻断；AI 只加审敏感路径 | 密钥/高危依赖阻断 | 低 |
| 5 人工审批 | 分类器定档 0/1/2 人 | 规则（+可选 LLM）定档；low=自审+冷静期，medium=自审逐条证据，high=外部 reviewer 记录 | 审批不满足阻断 | 低 |
| 6 合并与发布 | merge queue、flag、渐进、回滚 | rebase 后重跑确定性检查；Patch-ID 缓存策略；模板要求 flag 与回滚方案 | 检查/审批不满足阻断 | 无 |
| 7 学习闭环 | 事故即 eval，每日跑分 | outcomes 归档；golden set；每周 eval；夜间存量扫描不计入 PR 预算 | 回归告警，不阻断 PR | 低 |

说明：

- "安全发现即阻断"仅指密钥和高危依赖；Semgrep 按规则级别可配置阻断；AI 安全 finding 默认需要人确认，不直接阻断。
- 第 6 层的 merge queue / 部署系统不在本工具内，工具提供门禁状态与回滚辅助。

## 5. 主流程

### 5.1 run 阶段

| # | 阶段 | 输入 | 动作 | 输出 | 失败处理 |
|---|---|---|---|---|---|
| 0 | prepare | cwd、base、head、config | 解析 git 状态、diff、patch-id、变更文件、跳过路径；工作区脏则告警 | diff、stats、run_id | 配置/仓库错误 → exit 2 |
| 1 | checks | 配置的检查命令 | 并行/串行执行、收集输出、归档 artifact | check 结果与证据 | 阻断项失败 → 不调 AI，exit 1 |
| 2 | policy | diff 特征、路径、作者、配置 | 计算 tier、mode、预算、审批方式、理由 | policy decision | 无可降级理由的敏感路径强制 high |
| 3 | context | diff、变更文件、调用方、测试、文档 | 按 Finder 视角裁剪、脱敏、计算 hash | context bundle per agent | 超预算则裁剪；无内容 → 结束 |
| 4 | review | context bundles | Quick 单 Finder 或 Standard/Deep 多 Finder 并行 | candidate findings | 单 Finder 失败可降级；全失败 → incomplete |
| 5 | ground/dedupe | candidates | 校验文件/行号/变更范围；合并重复；过滤风格 | 去重后的 findings | 未通过 grounding 的记录为 rejected |
| 6 | verify | candidates | 批量验证、独立投票、聚合置信度 | confirmed / rejected / needs_human | 票数不足 → needs_human 或抑制 |
| 7 | report/store | 全量结果 | 写 ledger、SQLite、artifact、PR 评论/SARIF | 报告、账本、状态 | 存储失败 = run 失败（不可静默） |
| 8 | gate | findings、审批、冷静期 | 计算阻断与退出码 | gate 结果 | 未满足 → exit 3/4 |


### 5.3 幂等、缓存与取消

- 缓存键：`hash(context_hash + config_hash + prompt_versions + model_versions)`。同一内容命中时复用 AI 结果，但仍重跑确定性检查。
- 同一 PR 新 push：CI 使用 concurrency group 取消旧 run；本地 run 发现远端 head 变化时停止发布评论。
- 同一 run 重跑（重试）：按 `run_id` 幂等写账本，不重复扣预算、不重复发评论。
- rebase 且 patch-id 未变：复用 AI findings（记为 cached），重跑测试与安全检查；审批是否保留按档位规则（见 5.7）。
- 纯生成文件/锁文件/文档：按配置跳过或走轻量路径；锁文件仍执行依赖扫描。

### 5.4 风险分级

规则按顺序求值，命中即停；所有命中理由写入 `policy.reasons`：

1. 命中配置的 `tiers.high.paths`（`.github/workflows/**`、`auth/**`、`billing/**`、`scripts/release/**`、`migrations/**`、`infra/**` 等）→ **high**。该档位是硬地板，`--mode` 可升不可降；降低必须显式 `--override-high --reason ...` 并记录。
2. 删除测试文件、修改测试框架配置、修改 CI 配置 → 至少 **medium**。
3. 依赖清单/锁文件变更 → 至少 **medium**，强制依赖扫描；锁文件本身不送 AI。
4. 仅文档/测试文件（且无其他规则命中）→ **low**。
5. diff 行数（排除生成/锁文件）> 800 → 至少 medium；> 1200 → high 提示（默认仍 medium，可配置）。
6. 默认 **medium**。

可选的 LLM triage 只能在 low / medium 之间做仲裁，不能把规则判定的 high 降低；它的成本计入 run 预算，输出理由必须落入账本。

档位与审查模式默认映射（mode 可单独覆盖，但受 high 地板约束）：

| 档位 | 默认 mode | Finder | Verifier | 典型预算 |
|---|---|---|---|---|
| low | Quick | 1（correctness+security 合并视角） | 仅对 blocker/security candidate 触发轻验证 | 50k tokens |
| medium | Standard | 3（correctness / security / tests） | 3 票，≥2 确认 | 200k tokens |
| high | Deep | 4（+ api_contract）强模型 | 3 票，blocker 单条验证 | 500k tokens |

### 5.5 AI 审查与验证（摘要）

详细设计见《[技术可行性：多 Agent 协同](./技术可行性-多Agent协同.md)》。此处约束接口：

- Finder 输出结构化 candidate（文件、行、类别、severity、claim、evidence），不输出自由文本结论。
- Grounding 由代码确定性完成：文件存在、行号有效、代码片段 hash 匹配、位置在本次 diff 或允许的直接依赖范围内。
- Verifier 只收到 finding 的 claim/evidence、相关代码和验证指令，不收到 Finder 身份、置信度、模型名和其他票。
- 聚合规则：≥2/3 确认 → confirmed；≥2/3 拒绝 → rejected；其余 → needs_human（minor/nit 可抑制）。blocker/security 的平票必须进人工，不静默丢弃。
- 去重：`文件 + 类别 + 行区间重叠 + claim 文本相似度`；同 fingerprint 不重复发布。

### 5.6 收敛控制

- 轮次按 PR 计（每次推送触发一轮 AI 审查），上限 3 轮。
- 第 1 轮全量审；第 2 轮起仅审新增/变更 hunks + 未解决 finding 的相关文件，不再重发已有指纹。
- 同一 bug 类别要求"修复所有实例"，summary 按类别聚合提示；不针对单行打补丁。
- 达到上限仍有 blocker/important：停止自动复审，输出"退一步改方案"建议，要求人工 reset（`review reset-rounds --reason`，写入账本）后才能继续。
- 每次 push 后旧审批失效（按 diff hash）；重复 finding 只更新状态，不新增评论。
- 外层编码 Agent 的修复轮次共享同一 3 轮上限；循环协议见 [ADR-0002](./ADR-0002-开发Agent外层闭环.md)。

### 5.7 审批与冷静期

| 档位 | 审批人 | 冷静期 | 必须留存的证据 | 门禁 |
|---|---|---|---|---|
| low | self | 30 分钟（从 run 完成起算） | checks 全绿、测试输出、每个 finding 有处理结论、PR 清单勾选 | 冷静期内不得审批 |
| medium | self（逐条证据审阅） | 0–10 分钟（可配） | 同上 + 逐条 acknowledge blocker/important | 未 acknowledge 不得通过 |
| high | external reviewer | 不适用 | 外部审批记录 + 所有 blocker 关闭/显式接受风险 + 回滚方案 | 外部审批 + checks 全绿 |

- 审批记录包含：`run_id`、`diff_hash`、审批人身份（GitHub login 或本地声明）、审批类型、checklist 版本、时间、备注、已读 finding ID 列表。
- 审批入口：本地用 `review approve` 写账本；CI 场景用 PR label/评论（工具读取并校验时间与 diff hash），或将账本同步到专用分支后校验。
- 新 diff → 审批失效（`invalidate_on_new_diff: true`）；rebase 且 patch-id 未变时，low 可保留审批，high 默认仍需重新审批（更安全）。
- 身份限制必须诚实：本地审批只能"记录"外部 reviewer，无法证明身份；high 风险的强制力放在 CI，要求来自非作者的 GitHub review。单人仓库无法满足时，`allow_solo_override` 默认关闭；打开会写入 `override` 事件并在报告中标记。
- 冷静期由账本时间戳计算。CI 需要持久化的账本副本才能执行 `review ledger verify`：默认上传每次 run 的账本片段 artifact，推荐用专用分支（如 `review-ledger`）追加保存；未配置持久化时，门禁以本次 run manifest + GitHub 审批记录为准，本地账本只作审计导出（见 9.3）。

### 5.8 合并与发布

- rebase 后重跑确定性检查；AI 结果按缓存策略复用；rebase 与合并前必须有一次最新 head 的 gate 结论。
- PR 模板固定要求：feature flag 名称（如适用）、灰度计划、How to revert（命令或操作步骤）。
- 回滚辅助（P2）：`review revert --pr <n>` 生成并校验 `git revert -m 1 <merge_sha>` 命令、关联原 run 与事故标签；不自动推送。
- 合并队列、部署系统不重建；CI check 作为外部系统的 required gate。

### 5.9 评测闭环

```
PR merged → 记录 outcomes（fixed/dismissed/ignored/错误分类）
                │
历史回归 bug / 回滚案例 ──► golden set case
                │
每周 eval ──► recall、FP、成本、轮次指标 ──► 阈值与提示词调整
                │
             回归告警（recall 下降 >5pp 或 FP 上升 >10%）
```

- 评测不进入 PR 阻断路径，使用独立预算和夜间/周末时段。
- 提示词、模型、路由规则的任何修改都必须跑 eval 并记录结果（prompt hash 与 score 关联）。
- 夜间 `scan --since 30d` 只产出 backlog 报告，不刷 PR 评论。

## 6. 模块设计

### 6.1 CLI

| 命令 | 作用 | 里程碑 |
|---|---|---|
| `review run --base main` | 自动定档并跑完整流水线 | M1 |
| `review run --mode deep --budget 300k` | 强制模式/预算（高层级地板仍生效） | M1/M3 |
| `review checks` | 只跑确定性检查，输出证据路径 | M1 |
| `review report --run <id>` | 重新渲染报告（md/json/sarif） | M1 |
| `review approve --run <id> [--external --as <login>]` | 记录审批，校验冷静期与证据 | M3 |
| `review reset-rounds --reason "<...>"` | 重置轮次，写账本 | M3 |
| `review eval [--case <id>] [--update-baseline]` | 跑 golden set 并对比基线 | M3/M4 |
| `review scan --since 30d` | 存量扫描，独立预算桶 | M4 |
| `review outcomes [--since 30d]` | 统计 finding 处理结果与驳回分类 | M3 |
| `review ledger verify\|rebuild\|export` | 校验哈希链、重建读模型、导出 | M2/M3 |
| `review budget --month 2026-10` | 展示当月 token/金额与告警 | M2 |
| `review config validate` | 配置 schema 校验 | M1 |
| `review hooks install\|uninstall` | 生成/移除 pre-commit、pre-push hooks | M1 |
| `review gc` | 清理过期 artifact/cache | M2 |

退出码：

| 码 | 含义 |
|---|---|
| 0 | 审查完成、无阻断 finding、审批满足 |
| 1 | 存在阻断级 finding 或确定性检查失败 |
| 2 | 配置/内部/仓库错误 |
| 3 | 等待审批或审批失效 |
| 4 | 审查不完整（预算耗尽、AI 全失败、票数不足需人工） |

外层开发环的可选命令（`--fix-request`、`review loop`）见 [ADR-0002](./ADR-0002-开发Agent外层闭环.md)，不进入 M1–M4。

所有命令支持 `--json` 输出（P1），便于 Action 与脚本消费。

### 6.2 Pipeline Engine

```ts
interface RunContext {
  runId: string;
  repoRoot: string;
  config: ReviewConfig;
  budget: BudgetTracker;
  store: Store;
  signal: AbortSignal;
}

interface Phase<I, O> {
  name: string;
  run(input: I, ctx: RunContext): Promise<O>;
}
```

约束：

- 每个阶段结束提交一次账本事件；阶段可重入，不允许隐式全局状态。
- 所有外部调用（git、检查命令、模型 API）都有超时、并发上限和取消传播。
- 预算跟踪器按"预留 → 实际结算"扣减；模型调用前预留最大输出 token，防止超额。
- 任何存储失败视为 run 失败（exit 2），不允许静默丢弃审计记录。

### 6.3 Policy Engine

输入：diff stats、变更路径、是否删除测试、依赖变更、作者/提交者、配置覆盖、CLI 参数。
输出：

```ts
interface PolicyDecision {
  tier: 'low' | 'medium' | 'high';
  mode: 'quick' | 'standard' | 'deep';
  reasons: string[];
  sensitiveHits: string[];
  budget: { tokens: number; usdLimit: number };
  approval: { by: 'self' | 'self_evidence' | 'external'; cooldownMin: number };
  overrides: Array<{ flag: string; reason: string; by: string }>;
}
```

规则实现为纯函数，单元测试覆盖所有优先级；LLM triage 只能作为 low/medium 仲裁器，失败时回退 medium。

### 6.4 Checks 插件

```ts
interface CheckPlugin {
  name: string;
  kind: 'format' | 'lint' | 'type' | 'test' | 'secrets' | 'deps' | 'custom';
  shouldRun(ctx: CheckContext): Promise<boolean>;
  run(ctx: CheckContext): Promise<CheckResult>;
}

interface CheckResult {
  status: 'pass' | 'fail' | 'error' | 'skipped';
  blocking: boolean;
  durationMs: number;
  summary: string;
  evidencePath?: string;   // .review/artifacts/<run_id>/<check>.log
  findings?: RawFinding[]; // 可归一化的 lint/secret 结果
}
```

阻断矩阵：

| 检查 | 默认阻断 | 说明 |
|---|---|---|
| format | 是 | 仅检查变更文件 |
| lint | 是 | 允许按规则降级为 warning（需配置） |
| typecheck | 是 | 大仓库允许只跑受影响包（M3） |
| test | 是 | 失败必阻断；超时可配，超时视为 error |
| secrets | 是 | 发现即阻断，仅发送脱敏后的上下文 |
| deps | 高危/严重 | 低危告警；锁文件变更时强制运行 |

工具未安装：本地告警并按配置跳过或失败；CI 中缺失阻断工具视为配置错误。

### 6.5 Context Builder

输入：diff、变更文件完整内容、路径规则、repo map、CLAUDE.md / REVIEW.md、测试文件、直接调用方、PR 模板中的 What/Why（截断、脱敏）。

按 Finder 视角构造不同上下文：

| 视角 | 共享部分 | 专属部分 |
|---|---|---|
| correctness | diff、变更文件、PR 意图摘要、编码约定 | 调用方、相关测试、错误处理路径 |
| security | 同上 | auth/crypto/输入解析相关调用方、配置、依赖变更 |
| tests | 同上 | 测试文件、测试缺口、边界用例模式 |
| api_contract（Deep） | 同上 | 导出符号、调用方接口、兼容性相关测试 |

排序与预算（Context Builder 产出的上下文上限，含静态前缀与专属上下文）：Quick 24k / Standard 26k / Deep 50k tokens；system prompt、schema 与输出另预留约 4–5k。对应单 Agent 输入预算约 28–30k / 30k / 55k。

1. system / 审查规则 / REVIEW.md（静态前缀，可缓存）
2. diff（不截断，超限则整体降档或拒绝）
3. 变更文件完整内容
4. 相关测试
5. 直接调用方/被调用方
6. repo map（符号列表，非全文）
7. PR 意图摘要

裁剪顺序从低优先级开始；每次裁剪写入 `context.trimmed` 事件。所有上下文做脱敏并计算 hash；同一 run 的相同 bundle 复用缓存。

### 6.6 AI Layer（摘要）

- Router：按角色选模型（triage/quick/finder/verifier/deep），带预算与并发控制。
- Finders：并行的独立模型调用，无共享会话；每个视角一份 prompt；输出严格 JSON。
- Grounding/Dedupe：纯代码，无模型调用。
- Verifiers：批量（默认 3 条/调用，blocker 1 条/调用），独立投票，不互相可见。
- Aggregate：确定性规则 + 模板生成摘要；不让模型自由总结并决定是否阻断。
- 失败语义：见第 11 节。

### 6.7 Store

- `.review/ledger.jsonl`：事实源，append-only，事件带 `prev_hash` / `hash` 哈希链。
- `.review/state.db`：SQLite 读模型（runs、findings、approvals、evals、budget），可 `rebuild`。
- `.review/artifacts/<run_id>/`：检查日志、上下文清单、报告原文；默认保留 90 天。
- `.review/cache/`：按缓存键存 AI 结果；可清理。
- `.review/eval/cases/*.json`：评测样例，随仓库版本管理。

SQLite 表（核心列）：

| 表 | 关键列 |
|---|---|
| runs | run_id, pr_number, head_sha, base_sha, diff_hash, tier, mode, status, cost_usd, tokens, started_at, ended_at |
| findings | id, run_id, fingerprint, file, line, severity, category, status, confidence, resolution, created_at, updated_at |
| events | seq, run_id, type, payload, prev_hash, hash, ts |
| approvals | run_id, diff_hash, approver, approver_type, checklist_version, note, ts |
| evals | eval_id, case_id, run_id, matched, false_positives, cost_usd, ts |
| budget | period, bucket, tokens, usd |

### 6.8 Reporters

| 通道 | 内容 | 行为 |
|---|---|---|
| 终端 | 摘要、阻断项、证据路径、退出码 | 默认颜色输出，`--json` 可机读 |
| Markdown | 完整报告 + checks 证据 + 投票 + 预算 + 轮次 + 审批状态 | artifact，可贴 PR |
| GitHub Review | 一条 summary 评论（原地更新）+ blocker/important 行内评论 | 按 fingerprint 去重，不重复刷屏 |
| SARIF | 确定性检查与 AI findings | 供本地/合规导出；可上传代码扫描（视套餐） |

GitHub 严重度映射：blocker → `REQUEST_CHANGES` 级别评论 + fail check；important → 行内 comment；minor/nit → 仅在 summary 或 artifact。是否阻断由 `report.github.blocking_severities` 决定，默认仅 blocker。

## 7. 数据模型

### 7.1 Finding

```json
{
  "id": "f_01",
  "run_id": "r_20261031_01",
  "fingerprint": "sha256:3f9c...",
  "file": "src/auth/session.ts",
  "line": 42,
  "end_line": 44,
  "severity": "important",
  "category": "security",
  "claim": "token 未校验过期时间",
  "evidence": "session.ts:42 直接使用了 payload.exp，未与当前时间比较；调用链 verify() 无其他过期检查。",
  "suggestion": "在验签后检查 exp/nbf，并补充过期用例。",
  "confidence": 0.86,
  "votes": { "confirm": 2, "reject": 0, "uncertain": 1 },
  "sources": [
    { "agent_id": "finder_security", "model": "review-model@v3", "prompt_hash": "sha256:ab12..." },
    { "agent_id": "verifier_2", "model": "cheap-model@v1", "prompt_hash": "sha256:cd34..." }
  ],
  "grounding": {
    "file_exists": true,
    "line_in_changed_range": true,
    "snippet_sha256": "sha256:..."
  },
  "status": "confirmed",
  "resolution": null,
  "cost_usd": 0.012,
  "created_at": "2026-10-31T11:40:00Z",
  "updated_at": "2026-10-31T11:41:20Z"
}
```

枚举：

- `severity`: `blocker | important | minor | nit`
- `category`: `correctness | security | data | concurrency | performance | tests | api_compat | maintainability | docs | other`
- `status`: `candidate | ungrounded | confirmed | rejected | needs_human | reported | fixed | accepted_risk | dismissed | suppressed | duplicate | stale`

状态机：

```
candidate ──ground fail──► ungrounded
    │
    ├── verifier reject ──► rejected
    ├── 票数不足 ──────────► needs_human
    └── verifier confirm ──► confirmed ──► reported
                                               │
                     ┌─────────────────────────┼──────────────┐
                     ▼                         ▼              ▼
                   fixed                 accepted_risk    dismissed
                     │                         │              │
                     └─────────────► stale（代码已变更，未显式处理）
```

`duplicate` 与 `suppressed` 在 candidate 阶段产生；`stale` 由后续 run 检测到相关文件变更且未处理时写入。所有状态变化写账本。

## 9. 审计与合规

### 9.1 企业属性映射

| 企业属性 | 本方案实现 | 可导出的证据 |
|---|---|---|
| 每次变更都有检查 | 确定性检查 + AI 审查 + required CI check | check 结果、artifact、run 记录 |
| 有证据 | 测试输出、上下文 hash、投票记录、finding 证据 | Markdown/JSON/SARIF、artifacts |
| 有审批记录 | approval 事件绑定 diff hash、人、时间、checklist 版本 | approvals 表、ledger |
| 可回滚 | PR 模板回滚方案；`review revert` 辅助；feature flag 要求 | PR 模板字段、审批备注、revert 记录 |
| 可持续评测 | golden set、outcomes、每周 eval | eval 历史、指标报告 |
| 职责分离 | 全新上下文 + 冷静期 + high 档外部 reviewer；CI 强制非作者审批 | agent 调用记录、cooldown、审批身份 |

### 9.2 账本属性与边界

- 只追加、哈希链、可重建读模型；`review ledger verify` 可在 CI 中执行（前提是账本有持久化来源，见 9.3）。
- 记录提示词哈希与模型版本，不默认保存完整提示词（可配置保存脱敏快照）。
- 可导出 SARIF/JSON；保留期可配置（账本默认永久，artifact 默认 90 天）。
- 明确局限：单人环境无法强制职责分离；本地可伪造声明；哈希链不能阻止尾部截断。高风险场景以 CI 的 GitHub 身份与分支保护为准。

### 9.3 账本持久化与 CI 门禁

| 场景 | 账本位置 | 审批来源 | 审计能力 |
|---|---|---|---|
| 纯本地 | `.review/ledger.jsonl` | `review approve` 本地记录 | 本机完整；换机即丢失，需自行备份 |
| CI + artifact（默认） | 每次 run 上传 artifact | PR label/评论 + GitHub review | 覆盖 artifact 保留期；跨 run 查询弱 |
| CI + 专用分支（推荐） | 专用分支追加 `ledger.jsonl` | PR label/评论 + GitHub review + 账本 | 完整、可校验、可导出；多一次推送 |
| GitHub 作为审批事实源 | 本地/artifact 镜像 | 非作者 GitHub review / label | high 档强制的现实可行方案 |

约束：

- 不把账本直接提交到主分支（噪音、冲突）；用专用分支或 artifact。
- 专用分支写入失败时，high 档 gate 默认失败（宁可阻断，不丢失审计）；可配置为告警模式，但报告中必须标注"审批未持久化"。
- 工具在报告中明确当前账本模式，避免把"本地记录"误认为"CI 强制"。
- 账本可重建 SQLite 读模型，但账本是事实源；不要只备份 state.db。

## 10. 安全设计

| 威胁 | 场景 | 控制 |
|---|---|---|
| 提示词注入 | diff/注释中含"忽略以上指令" | 代码视为不可信数据；固定输出 schema；Agent 无工具；不执行模型命令；strip bidi/零宽字符；可疑内容记录并提示人工 |
| 密钥外泄 | diff 含 token，被发送云端 | gitleaks 先于 AI；命中即阻断；上下文脱敏；`never_send` 路径 |
| 数据外传 | 敏感仓库上传云端 | local_only 模式；路径白名单/黑名单；只送必要文件；可完全本地模型 |
| Fork PR 获取密钥 | GitHub Actions 暴露 secret | 默认 `pull_request` 不提供 secrets；fork PR 仅跑确定性检查；AI 审查需维护者显式触发 |
| 模型输出被当命令执行 | 输出测试命令/脚本 | 只解析 JSON finding；不 eval/执行；测试命令仅来自配置 |
| 供应链 | 依赖/扫描器被投毒 | 锁定依赖、pin Action SHA、扫描器官方版本；审查工具自身纳入 CI |
| 审计造假 | 手改账本/审批文件 | 哈希链、CI verify、审批绑定 diff hash；身份依赖 GitHub |
| 通知噪音导致误点 | 大量低价值评论 | 只对 blocker/important 行内评论，summary 原地更新 |

额外约束：

- API key 只从环境变量读取，不写配置文件、不进 artifact、不进日志。
- CI 中审查工具不获得写代码权限；需要发评论时使用最小 `pull-requests: write`。
- 本地运行不自动上传 `.review/` 之外的任何内容。
- 外层开发环：编码 Agent 在隔离 worktree/容器写，审查只读，测试/CI 文件受保护，禁止自动合并；见 [ADR-0002](./ADR-0002-开发Agent外层闭环.md)。

## 11. 降级与失败处理

| 场景 | 行为 | 退出码 / 门禁 |
|---|---|---|
| 确定性检查阻断失败 | 不调 AI，保存证据，报告失败 | 1，阻断 |
| 扫描器缺失/崩溃 | 视为配置错误；CI 阻断，本地提示修复 | 2 |
| AI 单 Finder 超时/失败 | 其余 Finder 继续；记录 coverage 降低；若至少一个成功，run 标记 degraded | 可继续，报告提示 |
| 全部 Finder 失败 | 降级为 checks-only，要求人工 | 4 |
| 验证票数不足 | important+ → needs_human；minor/nit → suppressed | 4 若存在 needs_human |
| 模型返回非 JSON | 一次修复重试；仍失败则丢弃该响应并记录 | 降级 |
| 预算 80% | 告警，停止低优先级验证/摘要 | 可继续 |
| 预算 100% | 硬停，保存部分结果，要求人工 | 4 |
| 月度预算超限 | 默认硬停 AI，仅跑确定性检查 | 4 |
| 存储写失败 | run 失败；不发布"通过"结论 | 2 |
| 新 push 取消旧 run | 旧 run 标记 cancelled，不发评论 | 不影响 |
| GitHub API 失败 | 报告写入 artifact；重试一次；gate 仍由 exit code 表达 | 2 / 人工 |
| 工作区脏 | 本地拒绝或仅审查已提交内容并告警 | 2 |

原则：任何"没有完成审查"的情况都不能被表达为"通过"。

## 12. 性能与成本

### 12.1 目标

| 项 | 目标 |
|---|---|
| Quick（400 行内） | p50 ≤ 2 分钟（本地，含检查） |
| Standard | p50 ≤ 4 分钟 |
| Deep | p50 ≤ 10 分钟 |
| 缓存命中 | ≤ 10 秒返回 AI 结果（仍跑检查） |
| 预算精度 | 单 run 不超上限；月累计可查询 |
| 账本开销 | < 1% 运行时间 |

### 12.2 预算与预期用量

| 档位 | 预算上限 | 预期使用 | 说明 |
|---|---|---|---|
| Quick | 50k tokens | 25–35k | 单 Finder |
| Standard | 200k tokens | 140–170k | 3 Finders + 9 次验证 |
| Deep | 500k tokens | 370–430k | 4 Finders + 更多验证 |

预算按"预留-结算"管理；缓存命中不重复扣减模型成本，但记录命中。月度账本按实际 usage 聚合，含扫描与 eval 的独立预算桶。

成本示例见《技术可行性》第 8 节；具体金额取决于模型定价，配置中的 `pricing` 是唯一计价来源。

## 13. 目录与技术栈

```
review-tool/
  package.json
  src/
    cli.ts
    engine/pipeline.ts
    engine/budget.ts
    policy/{risk,tiers,approval}.ts
    checks/{lint,test,secrets,deps}.ts
    context/builder.ts
    ai/{router,finders,grounding,dedupe,verifiers,aggregate}.ts
    store/{ledger,db,findings,evals}.ts
    report/{markdown,sarif,github}.ts
    providers/{openai,anthropic,local}.ts
  prompts/
    finder.correctness.md
    finder.security.md
    finder.tests.md
    finder.api_contract.md
    verifier.md
    repair_json.md
  tests/
    fixtures/
    golden/
.review/
  config.yml
  eval/cases/*.json
  state.db              # generated, gitignored
  ledger.jsonl          # generated, gitignored；可选同步到 review-ledger 专用分支
  artifacts/            # generated, gitignored
```

技术栈：

| 用途 | 选择 | 说明 |
|---|---|---|
| 语言 | TypeScript / Node ≥22 | 跨平台；团队熟悉 |
| CLI | commander | 轻量 |
| 校验 | zod | 配置与 Agent 输出 schema |
| git | simple-git + git CLI | patch-id、diff、rebase 检测 |
| 进程 | execa | 超时、取消、跨平台 |
| 并发 | p-limit | 全局并发上限 |
| 路径匹配 | picomatch | 与 gitignore 类似的 glob |
| 存储 | JSONL + better-sqlite3 | Node 24 也可评估内置 `node:sqlite` |
| 测试 | vitest + 录制式 fake provider | 确定性、零 API 成本 |
| CI | GitHub Actions | 免费额度；`pull_request` |
| hooks | 原生 git hooks（`review hooks install`）；lefthook 模板可选 | 跨平台；不覆盖用户已有 hook |
| 安全 | gitleaks / Semgrep / osv-scanner | 官方二进制/容器 |
| 模型 | 兼容 OpenAI/Anthropic/本地 OpenAI-compatible | Provider 适配层 |

不引入 Agent 编排框架（选型依据见 [ADR-0001](./ADR-0001-编排框架选型.md)）；固定 DAG 用几百行编排代码即可，可读、可测、可审计。

## 14. 里程碑与验收

| 里程碑 | 范围 | 验收标准 | 预估 |
|---|---|---|---|
| M0 | CLAUDE.md/REVIEW.md、PR 模板、pre-commit/pre-push、diff 规模规则文档 | hook 能阻断 lint/type/test 失败；PR 模板强制五项；无工具代码 | 0.5 天 |
| M1 | CLI + 确定性检查 + Quick Finder + blocker/security 轻验证 + JSON 修复重试 + JSONL 账本 + Markdown 报告 + 预算 + hooks install + 配置校验 | 在 10 个历史提交上可重复运行；证据完整；预算硬停；跨平台；Quick p50 ≤2 分钟 | 1–2 天 |
| M2 | 风险分类器 + Standard（Finders/Verifiers）+ grounding/dedupe + GitHub Action 评论 + diff 门禁 + SQLite + 缓存 | 敏感路径强制 high；重复评论为 0；finding 有投票记录；CI required check 生效；eval harness 可跑通 | ~1 周 |
| M3 | 安全扫描 + Deep + 审批/冷静期 + 轮次收敛 + rebase 策略 + ledger verify/export + outcomes | high 不能自审；新 push 使审批失效；3 轮自动停止；密钥阻断；SARIF 导出 | 1–2 周 |
| M4 | golden set ≥30 例、每周 eval、夜间扫描、指标与误报归因、阈值调优；用数据决定多 Agent/Deep 比例 | 指标可查询；eval 回归告警；无证据不扩大 AI 档位 | 持续 |

M1 刻意不引入 SQLite、独立多 Verifier 投票、GitHub 评论，先证明"确定性检查 + Quick Finder + 轻量验证 + 证据 + 预算"闭环；M2 再补多视角协作与集成。

外层开发 Agent 闭环（编码 Agent ↔ 测试 ↔ 审查）为可选实验，见 [ADR-0002](./ADR-0002-开发Agent外层闭环.md)，不进入 M0–M4 核心验收。

## 15. 风险与开放问题

### 15.1 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| AI 噪音导致审查疲劳 | 忽略真问题 | 严格 grounding、投票、只发布重要项、outcomes 统计 |
| 多 Agent 成本翻倍但收益有限 | 预算超支 | 分档启用；eval 决策；多 Agent 只用于 Standard/Deep |
| 提示词注入 | 错误结论/越权 | 无工具、结构化输出、不可信数据框定、人工复核 |
| 模型升级导致行为漂移 | 质量波动 | 固定版本；prompt/model hash 入账；eval 回归 |
| 高风险审批流于形式 | 审计失真 | CI 强制非作者审批；cooldown；账本校验；solo override 显式标记 |
| 大 diff 上下文不够 | 漏报 | diff 规模门禁；Direct caller 检索；Deep 档；拒绝假装覆盖 |
| 单人维护范围蔓延 | 项目半途 | 严格 M0–M4；非目标清单；每阶段可独立使用 |
| Windows 工具兼容性 | 本地体验差 | Node 实现、原生 hooks/lefthook 模板、官方二进制；CI 矩阵测试 |

### 15.2 开放问题

1. 首发支持的语言/生态（建议先 Node + Python，测试命令除 package.json 外保持配置化）。
2. 模型供应商与预算币种；是否需要双供应商降低单点故障。
3. 外部 reviewer 在个人项目中的实际来源；是否接受"社区 reviewer + 冷静期"作为 high 档的替代。
4. 是否在 Deep 档引入只读代码检索工具（会扩大攻击面与成本）。
5. 多仓库统一账本的位置（M4 之后再考虑，不引入服务端）。
6. UI 变更截图证据是否纳入自动检查（建议 PR 模板人工提供，暂不自动化）。
