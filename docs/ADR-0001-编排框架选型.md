# ADR-0001：Agent 编排框架选型

- 状态：Accepted
- 日期：2026-10-31
- 决策：自写编排，不引入 Agent 编排框架（M1–M3）
- 关联：[设计文档](./设计文档.md) §3.4 / §13 · [技术可行性：多 Agent 协同](./技术可行性-多Agent协同.md) §10.1 / §14 · [ADR-0002 外层开发闭环](./ADR-0002-开发Agent外层闭环.md)

---

## 1. 背景

代码审查流水线已经明确为固定 DAG：

```
prepare → checks → policy → context → Finder fan-out → Grounding/Dedupe
→ Verifier fan-out → Aggregate → Store/Report → Gate
```

关键约束：

- Agent 是一次无状态、无工具、无网络/文件系统访问的结构化模型调用。
- 审查内部 Agent 之间不直接对话，编排器是唯一路由者。
- 预算、append-only 账本、审批绑定、prompt/模型版本、deterministic replay 必须自管。
- TypeScript / Node ≥22，Windows/macOS/Linux，本地优先，CI 使用 GitHub Actions。
- 单次审查通常数分钟；审批发生在 run 之后，不要求图内暂停。

本 ADR 回答两个问题：用不用现成 Agent 框架；如果用，选哪个。

## 2. 硬门槛

任一不满足即淘汰：

| ID | 门槛 |
|---|---|
| G1 | TypeScript/Node ≥22，Windows/macOS/Linux 可运行 |
| G2 | 不强制常驻服务端或外部数据库服务，支持本地优先 |
| G3 | 能实现固定 DAG；审查 Agent 不持有工具/网络/文件系统；无自由 agent 对话 |
| G4 | 供应商中立，可统一注入不同模型客户端与 usage 统计 |
| G5 | 账本、预算、审批、prompt/context hash、fake provider/replay 可由自研代码完全掌控 |
| G6 | 所有模型调用可被路由器拦截；不存在隐藏的框架内部 LLM 调用 |

## 3. 对比矩阵

| 候选 | 语言/运行 | 编排模型 | G3 固定 DAG/无工具 | G5 审计/预算 | G4 供应商中立 | 判定 |
|---|---|---|---|---|---|---|
| 自写编排 | TS/Node | 显式 async 状态机 | 完全满足 | 完全掌控 | 完全满足 | **采用** |
| LangGraph.js | TS/Node | 图 + state + checkpointer + interrupt | 可满足 | 部分：状态与账本并行 | 可满足（节点内可用原始 SDK） | **后备 1** |
| Mastra | TS/Node | workflow + step + suspend/resume | 可满足 | 部分：框架状态/观测额外一层 | 可满足（经 AI SDK） | **后备 2** |
| OpenAI Agents SDK | TS/Node | 动态 agent loop、handoffs | 部分/不契合：编排语义不是图 | 低：需全程自建并绕过框架循环 | 以 OpenAI 为中心 | 不采用 |
| Claude Agent SDK | TS/Python | Claude Code 自主循环 + tools/subagents | 不契合：运行时自带工具循环 | 低：工具面与运行时不可审计性增加 | Claude 运行时绑定 | 不采用 |
| Microsoft Agent Framework | .NET/Python/Go | agents + graph workflows | 可满足（但语言不符） | 中等 | 可满足 | G1 失败，淘汰 |
| CrewAI | Python | Crews + 事件驱动 Flows | 部分（语言不符） | 低–中 | 可满足 | G1 失败，淘汰 |

补充说明：

- 表中的“可满足”是**能力上可实现**，不代表引入后不增加风险；G5 对所有框架都只能部分满足，因为账本/预算/审批本来就不在框架的抽象内。
- Microsoft Agent Framework 的官方概览写明支持 .NET、Python、Go，未列 TypeScript。
- CrewAI 是 Python 框架，Crews 偏角色协作，Flows 才偏确定性工作流。

## 4. 逐项评估

### 4.1 自写编排（采用）

- 角色与阶段在代码里显式可见；没有额外状态、没有隐藏调用。
- 账本、预算预留/结算、审批、prompt hash 是同一套代码，审计链不会分裂。
- fake provider 可在路由器层注入，测试与回放成本低。
- 预估 500–800 行核心编排，远低于引入与维护框架的成本。
- 代价：需要自己实现超时、重试、取消、并发限制；这些已列入 M1 范围，且逻辑简单。

### 4.2 LangGraph.js（后备 1）

官方文档提供 checkpointers 与 interrupts/HITL，适合“图 + 状态 + 人工介入”的场景。

不现在采用的原因：

- checkpoint 状态会与 JSONL 账本并存，需要额外定义“谁是事实源”；我们把账本定为事实源，checkpoint 只能是缓存。
- framework 的消息包装可能改变 prompt 字节，影响 prompt hash 与 replay；采用前必须验证规范化边界。
- 当前 run 短、审批在 run 后，不需要 interrupt/durable checkpoint。
- 引入 LangChain 生态依赖、版本升级与 Windows 兼容成本，收益不足以抵消。

若未来需要图内 HITL、跨进程恢复或可视化，优先重新评估它；采用时只作为执行层。

### 4.3 Mastra（后备 2）

Mastra 是 TypeScript 原生的 Agent/工作流框架，官方文档提供 workflow、suspend/resume、snapshots，且有 agents、evals、observability 等更大的一体化面。

不现在采用的原因：

- 我们不需要 suspend/resume；审批是 run 后独立事件，不是图内等待。
- 一体化面越大，越可能重复实现或绕过我们的账本/预算/路由；需要更多审计。
- 版本与生态较新，Windows/Node 兼容、默认遥测、存储适配都要先验证。
- 若采用者更看重 TS DX 与 evals 一体化、且 LangGraph.js 的生态/依赖不合意，可把它作为第二候选做 spike。

### 4.4 OpenAI Agents SDK（TS，不采用）

官方定位围绕 agents、handoffs、guardrails、sessions、tracing；核心是 agent 运行循环与 handoff，不是显式阶段图。

- 我们的设计禁止 handoff/agent 对话，且每个“agent”只是一次结构化调用；SDK 的主要抽象用不上。
- tracing/sessions 会引入与供应商平台耦合的观测面，且不是我们的审计格式。
- 若只把它当单次调用封装，又没有足够收益；保留官方 OpenAI SDK 作为 provider 更直接。

### 4.5 Claude Agent SDK（不采用）

它运行 Claude Code 的 agent loop，带内置工具、permissions、hooks、subagents 与会话。它适合让 Claude 自主操作代码，不适合“无工具、固定 DAG、供应商中立”的审查器。把工具全关掉后，只剩 Claude 模型封装的成本，不如直接用 Anthropic API/SDK 作为 provider。

### 4.6 Microsoft Agent Framework（淘汰）

官方概览显示支持 .NET、Python、Go，并区分 agents 与 graph workflows，提供 state/HITL 等能力。语言不满足 G1，且会引入新的平台依赖；不进入候选。

### 4.7 CrewAI（淘汰）

Python 框架，Crews 以角色协作为主，Flows 提供更确定的事件驱动工作流。语言不满足 G1，角色协作拓扑也与星型编排不符；不进入候选。

## 5. 决策与 Agent 角色

### 5.1 决策

1. M1–M3 使用 TypeScript 自写固定 DAG，不引入任何 Agent 编排框架。
2. 模型接入使用官方 SDK 或薄 fetch 适配层（OpenAI / Anthropic / 本地 OpenAI-compatible），不引入 Vercel AI SDK 等额外抽象作为编排依赖。
3. 借框架的“模式”而不借依赖：显式状态机、阶段 checkpoint 写账本、AbortSignal 取消、重试/退避、预算预留/结算、fake provider、结构化 schema。
4. 框架只在满足第 7 节条件时重新评估；任何框架都不得拥有账本、预算、审批或 prompt 规范化的所有权。

### 5.2 哪些 Agent

| 角色 | 数量 | 职责 | 模型档 |
|---|---|---|---|
| Triage（可选） | 0–1 | 仅在 low/medium 规则难判定时仲裁；不能把 high 降级 | cheap |
| Finder | 1 / 3 / 4 | 按 correctness/security/tests/api_contract 视角独立找问题；无工具、无对话 | quick/finder/deep |
| Verifier | 0 / 3 / 3 | 独立 refute-first 投票；不接收 Finder 身份、置信度、其他票 | verifier（cheap） |
| Aggregator | 1 | 确定性投票聚合、severity/状态机；不调用模型 | 无 |
| Orchestrator | 1 | 阶段调度、预算、取消、账本、报告 | 无 |

明确不做（审查内部）：manager agent、handoff、agent 间自由对话、工具调用型审查 Agent、图内 debate。外层编码 Agent 的修复环见 [ADR-0002](./ADR-0002-开发Agent外层闭环.md)。

## 6. 若未来采用框架的边界规则

- 框架只负责执行步骤与传递状态；账本、预算、审批、prompt hash、报告由自研代码维护。
- 所有 LLM 调用必须经自研 Router；禁止框架内部发起未经预算预留的调用。
- 发送前对规范化消息计算 hash；记录模型精确版本；框架不得在不知情处追加系统消息。
- fake provider 必须能在框架层注入；无法注入则不采用。
- 默认 telemetry/observability 必须可关闭，并在隔离网络下验证无外传。
- checkpoint 是缓存，不是审计事实源；需要时可导出到账本。
- 采用前通过三平台 CI、Node ≥22、无服务端模式、许可证与供应链检查。

## 7. 切换触发条件

满足任一条件才重新评估：

1. 需要跨进程/崩溃恢复，或单次审查超过 30 分钟、引入队列或常驻服务端。
2. 人需要在 **run 中途** 审批/补充上下文，而不是 run 后审批。
3. 编排拓扑按仓库动态变化，而非仅 Finder 数量/视角变化。
4. 自研编排超过约 1.5–2k 行且持续出现状态机 bug；或团队扩到 3 人以上，需要可视化/统一调试。
5. 候选框架通过第 6 节边界测试与第 2 节硬门槛。

若触发：先评估 **LangGraph.js**；若更看重 TypeScript 原生工作流、suspend/resume、evals 的一体化，再评估 **Mastra**。两者都只作为执行层。

## 8. 未验证项（采用前必须确认）

- LangGraph.js / Mastra 的当前版本对 Node 22、Windows 的实际支持。
- 默认 tracing/telemetry 是否开启、能否完全关闭、是否代理可验证。
- 框架在消息构造中是否追加 system/developer 消息，是否影响 prompt hash。
- fake provider 注入点是否覆盖框架内部所有模型调用。
- checkpointer/storage 后端是否引入常驻数据库或额外运维。
- 许可证、发布频率、维护者数量与供应链风险。
- Mastra 的 workflow fan-out/聚合语义与错误传播细节是否满足我们的预算与取消要求。
